## 1. Production Readiness

### Build & type-check
`npm run build` (`tsc -b && vite build`) fails with the same 7-file list documented in this agent's own definition — re-confirmed this run, list unchanged. All 7 failures are the identical shape: a shadcn/Radix component (`Button`, `Chip`, `List` from `src/components/ui`) receiving an MUI-only `sx` prop it doesn't accept, because the calling page/section was never migrated off the MUI calling convention when the underlying component was swapped to shadcn. This is a coexistence-boundary problem, not 7 unrelated bugs — fixing the pattern once (add an `sx`-to-`className`/`style` shim, or finish migrating the 7 call sites) closes all 7.

**Separately, this branch's working tree is not build-clean for reasons unrelated to the above:** `git status` shows uncommitted changes to `src/tokens.ts` and `src/semantic-tokens.ts` (adds `focusBlue`/`focusBlueDark`/`surfaceSecondaryHover`, changes `gold750`/`brandAccent`/`textOnHero`/`surfaceHero`/`borderFocus`/`focusRing`). These are legitimate in-progress token work, but until committed (with the required token-diff review) they cause `tokens:check`'s CI-policy diff step to fail and cause 4 vitest snapshot tests to fail (see Tracked Deferred Items DEFERRED-009). This is presumably transient WIP, not a structural gap — but it means *today's* branch state cannot pass CI even setting aside the 7 build errors above.

### Accessibility enforcement
`@storybook/addon-a11y` is registered (`.storybook/main.ts:20`) and `eslint-plugin-jsx-a11y` is a `package.json` devDependency, but neither is wired into anything that runs unattended: no `test-storybook` script in `package.json`, no CI step in any of the 7 active workflows references `a11y`, and `eslint.config.js` has zero references to `jsx-a11y` — the plugin is installed but not registered as a plugin/ruleset. ### Contrast — confirmed-failing pairs beyond the ones already in Tracked Deferred Items
Computed fresh (WCAG relative-luminance formula, same as `scripts/check-contrast.js`) rather than trusting the prior session's numbers verbatim:
- `Button.tsx` `destructivePrimary`: `bg-[#c53532] text-white` (hardcoded Tailwind arbitrary values, line 49-50, no dark-mode class variant). White-on-`#c53532` = 5.34:1 (passes). But `statusDanger`'s own dark-mode value is `tokens.red500` / `#ff6b6b` (`semantic-tokens.ts:173`) — white against that is 2.78:1 (fails 4.5:1). Because the button hardcodes the hex rather than calling `getRoleColor('status.danger')`, it structurally cannot pick up dark-mode role overrides at all — `check-contrast.js` only reads compiled `tokens.json`, never component source, so this class of bug is invisible to the existing gate regardless of what pairs get added to it.
- `Checkbox.tsx` checked+invalid (`checkbox.tsx` line ~112-122): background = `interactive.danger` role, icon color = `text.onAccent` (white). Light: white on `#e53935` (interactiveDanger light) = 4.23:1 — fails the 4.5:1 text threshold. Dark: white on `#ff6b6b` = 2.78:1 — fails outright.
- `mega-menu.tsx:114` (new this run, see Changelog): `backgroundColor: surface.accent, color: text.inverse` on a nav-link badge pill — same 1.06:1 light-mode failure pattern just fixed elsewhere, missed in this file.
