# Governance

This repo enforces three separate, interlocking governance systems. Each one exists to catch a different kind of drift, and each has its own detailed doc — this page is the map between them, with the visual flow each one is missing on its own.

## 1. Token & role governance

**What it protects:** that every color in the codebase traces back to an approved token, through the 3-tier architecture — never a hardcoded hex value.

<TokenGovernanceFlow />

**Needing a new token that doesn't exist yet** is a separate, upstream decision — design/approval, not enforcement. That flow (which layer, who signs off, how long it takes) is fully mapped in **`docs/TOKEN_REQUEST_DECISION_TREE.md`**, with the written process in **`docs/TOKEN_REQUEST_PROCESS.md`**. This diagram is the other half: once a token *does* exist, what stops someone from bypassing it.

### Checked by

| Command | Checks |
|---|---|
| `npm run roles:check:strict` | Any component importing `tokens.*` or `semanticColors.*` directly, a dangling `--role-*` variable, or a hex literal in `src/components/ui/` source |
| `npm run tokens:check` | Token build succeeds, no unauthorized primitive diff, DTCG export valid, WCAG contrast on every enforced pair |
| `npm run governance:ci` | Every gate below, bundled — this is what `governance.yml` runs in CI |

Full architecture, naming rule, and dark-mode mechanics: [Roles](?path=/docs/foundations-roles--docs), [Colors](?path=/docs/foundations-colors--docs), and **`docs/foundations/TOKENS.md`**.

## 1b. The gates that check the gates

**What it protects:** that a green result means something.

Every gate in this repo that has ever been wrong was wrong the same way — it
measured something *adjacent* to what it claimed, and reported green while the
real defect shipped. The axe gate once ran **zero** checks across every story.
The role gate parsed **6 of 55** role names. The registry gate checked index
entries rather than dependency edges. A published release shipped an
`index.d.ts` that did not compile, with all eight gates green.

A green gate is indistinguishable from a disabled one unless something asserts
otherwise. So two harnesses do the asserting, and both run in `governance:ci`.

| Command | Checks |
|---|---|
| `npm run gates:selftest` | Writes a probe containing one real violation per gate, runs the gate, and requires it to exit non-zero **and name the probe**. Exiting non-zero alone is not evidence — a crash, a malformed probe, or an unrelated pre-existing violation all look like a healthy gate |
| `npm run metrics:selftest` | The same idea for the 14 `ds:score` metrics, in **both** directions: a change that should move a metric must move it, and one that should *not* must leave it exactly alone |
| `npm run ds:score` | The health score itself — 14 frozen formulas grouped by goal (development readiness, governance, scalable global system, AI-agent readiness), readable at any git revision so history is backfillable |

The second direction is the one that earns its keep. A metric is a *number*,
and a number can move for the wrong reason: `prop_docs` was once satisfied by
14 docblocks sitting in **empty interface bodies**, which react-docgen cannot
turn into a prop description. The metric moved 44 → 80 while the thing it names
did not budge. Only a probe asserting "this change must *not* count" catches
that.

Adding a gate means adding its probe; adding a metric means adding both of its
probes. That is deliberate friction.

## 2. CI quality gates

**What it protects:** that nothing broken — a failing test, a type error, an undocumented token change, a bad commit message — reaches `main`, regardless of which branch it was written on.

<CIGatesFlow />

Push triggers are deliberately **not** `main`-only — this repo does substantial work directly on feature branches, so every branch gets real signal instead of nothing until merge.

**Reproduce any of this locally** before pushing — the exact command for each step is on [Testing](?path=/docs/foundations-testing--docs), and the README's CI & Quality Gates section has the full failure cheatsheet.

## 3. Documentation governance

**What it protects:** against exactly what already happened once in this repo — ~70 one-off status reports and build summaries accumulating at the repo root because nothing told anyone where a new doc belonged. `docs:check-sprawl` is the mechanical backstop; the decision ladder below is what actually prevents a new doc from needing to be moved later.

<DocPlacementFlow />

The mechanical gate (`docs:check-sprawl`, run as part of `docs:lint` in every CI run) only catches the literal failure mode — a new `.md` file landing at repo root outside the five allowlisted files. It can't enforce "does an existing doc already cover this" or "has this doc gone stale" — those need judgment, which is what the ladder above is for. Full text version, with the actual list of examples this rule already fixed: **`CLAUDE.md` → Documentation Governance**.
