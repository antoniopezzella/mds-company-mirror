# Marsh Design System

Three things to know before you write any code here:

1. **Colors always go through a role, never a hex value.** `getRoleColor('interactive.primary')`, not `#000f47`. This is enforced by `npm run roles:check` in CI — see [Colors](?path=/docs/foundations-colors--docs).
2. **Layout is plain Tailwind grid utilities.** `grid grid-cols-12 gap-6`, not custom CSS. There's an older, unrelated grid system still used by a handful of legacy pages — if you're building something new, you don't need it. See [Grid](?path=/docs/foundations-grid--docs).
3. **Building UI? Check for an existing component first.** Every component in the current component library — buttons, forms, dialogs, tables, everything — is browsable with live examples and "use this / not that" guidance at `/design-system` (run the app, see below). Don't build something that already exists.

## Run it

```bash
npm install
npm run dev         # the app, http://localhost:5173
npm run storybook   # this documentation, http://localhost:6006
```

## Starting a new page

1. **Check `/design-system` first.** Does what you need already exist? Does an existing component's props already cover it (a new `variant`/`tone`/`size` beats a new component)? Can you compose two or three existing ones? Only build new as a last resort.
2. **Add a route.** `src/Router.tsx` is a flat list — lazy-import your page, add one `<Route>`.
3. **Build with what's in `src/components/ui/`**, laid out with Tailwind grid, colored with roles:

```tsx
import { Card, CardHeader, CardTitle, CardContent } from '@/components/ui/card';
import { Button } from '@/components/ui/button';
import { getRoleColor } from '@/theme/roles';

export default function HelloPage() {
  return (
    <div className="grid grid-cols-1 md:grid-cols-3 gap-6 p-6">
      <Card>
        <CardHeader>
          <CardTitle style={{ color: getRoleColor('fg.primary') }}>
            Hello
          </CardTitle>
        </CardHeader>
        <CardContent>
          <Button variant="primary">Take action</Button>
        </CardContent>
      </Card>
    </div>
  );
}
```

That's the whole pattern: components from `@/components/ui/*`, `grid`/`gap-*` for layout, `getRoleColor()` for any color that isn't already baked into the component. No `sx` prop, no CSS Modules, no hex values.

Full walkthrough, route to finish: **`docs/get-started/BUILD_YOUR_FIRST_PAGE.md`**.

## Beyond building pages

The workflow above (`components/ui/*` + roles + Tailwind grid) covers most day-to-day work. This system also does several things that aren't visible from that workflow alone — easy to miss if you only ever look at the component docs:

- **Testing** — every `.stories.tsx` file doubles as a real test, rendered in an actual Chromium browser via Playwright (`@storybook/addon-vitest`), not just a visual example — on top of the usual `jsdom` unit tests. No extra test files to write; `npm test` runs both. Full guide, including coverage and running it from Storybook's own UI: [Testing](?path=/docs/foundations-testing--docs).
- **Figma Code Connect** — real component source shown directly in Figma Dev Mode, so a designer inspecting a component in Figma sees the actual React code, not a guess. Setup and mapping files: `docs/FIGMA_CODE_CONNECT_GUIDE.md`, `src/figma/*.figma.tsx`.
- **MCP-driven Figma sync** — pulls live Figma Variables straight into an interactive session (via the Figma Desktop Bridge MCP server) and diffs them against the token values actually shipping in code — catches drift between what Figma says a color should be and what's real. Re-checkable anytime without a live Figma connection: `npm run tokens:check-figma` / `tokens:check-figma-semantic`, against the snapshots in `src/figma-variable-map.json` / `src/figma-variable-map-semantic.json`. `docs/FIGMA_PRIMITIVE_TOKEN_ASSESSMENT.md` and `docs/FIGMA_SEMANTIC_TOKEN_ASSESSMENT.md` are real worked examples of what this surfaces.
- **`agents/design-system-agent`** — a separate, unattended pipeline: point it at one Figma component node, it builds an MDS-compliant, PR-ready component headlessly — for a webhook, CI job, or scheduled sweep, not interactive use. Enforces `CLAUDE.md`'s rules structurally (per-subagent filesystem permission allowlists), not just by convention. See its own `agents/design-system-agent/README.md`.
