# Theming — light, dark and inverse

Every colour in MDS changes with the theme on its own. You never write a dark-mode
rule: you reference a role or an MDS class, and the value behind it is redefined
when the theme changes.

This page is about the one thing you do have to know — **what switches the theme**,
and the two places where that is not yet uniform.

---

## The rule

> **Never write `dark:` for a colour.** The variable already flips. A `dark:`
> colour class is a second, hand-maintained answer that will disagree with the
> first one eventually.

```jsx
// ✅ flips on its own
<div className="bg-default text-primary" />
<div style={{ color: roleVar('fg.critical') }} />

// ❌ two answers for one decision
<div className="bg-white dark:bg-neutral-900" />
<div style={{ color: isDark ? '#ceecff' : '#000f47' }} />
```

`dark:` is still correct for things that are *not* colour — a shadow, an opacity,
a border width you genuinely want different in dark.

---

## What switches the theme

Three mechanisms, and they do not all reach the same layers. This matters the
moment you nest one theme inside another.

| Mechanism | Where it goes | What it switches |
|---|---|---|
| `data-theme="light｜dark"` | `<html>` | The generated token layer (`--mds-color-*`) |
| `.dark` class | `<html>` | The generated layer, **plus** the role tier (`--role-*`), the shadcn variables, and Tailwind's `dark:` variant |
| `data-surface="light｜dark｜inverse"` | any element | The generated token layer only — **not** `--role-*` |

The app writes **both** `data-theme` and `.dark`, so in normal use you never think
about the difference. `ThemeModeProvider` sets them together, and `index.html`
sets them before first paint so the very first render is already correct.

### Why both

`data-theme` is the mechanism the generated layer is built on, and it is what a
nested surface needs. The `.dark` class is the contract the **published package**
ships — `darkMode: ['class']` and `@custom-variant dark (&:is(.dark *))` — so a
consuming app that follows our docs and sets a class gets correct colours. Drop
either one and half the system stops following the theme.

---

## Nesting a surface

A navy band inside a light page, or a light card inside that band:

```jsx
<section data-surface="dark">      {/* dark band in a light page */}
  <Card data-surface="light" />    {/* light card inside the band */}
</section>
```

Inside the band, every `--mds-color-*` resolves to its dark value, so MDS classes
(`bg-default`, `text-primary`, `border-subtle`) are correct automatically.

> **Known limitation.** `--role-*` does **not** respond to `data-surface`. The role
> tier is emitted only for `:root` and `.dark`, so inside a `data-surface` band a
> component styled with `roleVar('bg.default')` keeps the **page** theme while a
> component styled with `bg-default` takes the **band** theme. Mixing the two in
> one nested surface will not look right. Until the role tier gains the attribute,
> style nested surfaces with MDS classes.

## Two ways to read a colour in JS

```jsx
import { roleVar, getRoleColor } from '@/theme/roles';

style={{ color: roleVar('fg.primary') }}              // var(--role-fg-primary)
style={{ color: getRoleColor('fg.primary') }}          // '#000f47'
```

**Prefer `roleVar()`.** It emits a variable reference, so the value follows the
theme through the cascade and a consumer can retheme it.

**`getRoleColor()` bakes a literal** into the DOM. Nothing can retheme it
afterwards, and it decides the mode by reading `<html>` at render time. Reach for
it only when you need the actual string — a canvas fill, a contrast calculation —
or when you are forcing a mode on purpose:

```jsx
// The side-nav rail is dark inside a light page, so it needs the dark value
// baked in. A variable here would follow the page and turn the rail white.
getRoleColor('bg.neutral.subtle', { mode: 'dark' })
```

Those seven calls in `side-navigation.tsx` are the only `getRoleColor` left in the
published component set; everything else resolves through variables.

## Inverse

`[data-surface="inverse"]` is a third set of values in the token layer, carried in
the Figma export alongside Light and Dark. The CSS is live today.

The **JavaScript** side is not: `ThemeMode` is `'light' | 'dark'`, so
`getRoleColor(role, { mode: 'inverse' })` does not type-check and
`ThemeModeProvider` cannot be put into it. Inverse is usable as a nested surface,
not as a page mode.

## What is enforced

You do not have to remember most of this — the gates fail if it drifts.

| Check | What it would catch |
|---|---|
| `pins:check` | A pinned role whose shipped CSS disagrees with the Figma export, in either mode |
| `pkg:css:selftest` | The published stylesheet losing its `.dark` binding — which would silently give every consumer light colours |
| `dark:check` | A story that fails accessibility in dark mode and was not already failing |
| `tokens:contrast:all` | An enforced foreground/background pair dropping below its ratio in either mode |
| `roles:check:strict` | A hardcoded hex or a Tailwind palette class in `src/components/ui/` |

## If a colour does not flip

1. **Is it a hex?** Search the component for `#`. A literal cannot flip.
2. **Is it a `dark:` class?** Delete it and use the role or MDS class alone.
3. **Is it `getRoleColor()` without a mode?** It baked the value at render. Use
   `roleVar()` instead.
4. **Is it inside a `data-surface` band?** See the limitation above — role
   variables do not follow `data-surface`.
5. **Is it a consumer app?** Confirm the host sets `.dark` on `<html>`, not only
   `data-theme`, and that it imports the package stylesheet.
