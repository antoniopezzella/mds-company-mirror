# Spacing

Everything in this system sits on a **4px grid**. There is one grid and two ways
to write it, because the component set spans two styling tracks.

The important thing to know up front: **Tailwind's default spacing scale is
already a 4px grid.** That is why `tailwind.config.js` does not extend
`spacing` — it does not need to. Every step in the MDS scale is reachable with
a stock Tailwind class, exactly.

Since the v4 upgrade the whole scale derives from one variable:

```css
--spacing: 0.25rem;                    /* 4px */
.p-4 { padding: calc(var(--spacing) * 4) }   /* 1rem */
```

Practically that means the entire grid can be retuned from a single value — a
denser build could set `--spacing: 0.1875rem` (3px) and every utility follows.
Nothing here does that today, and it should not be done casually, but it is
worth knowing the lever exists.

## Which API to use

| You are working on… | Use | Example |
| --- | --- | --- |
| **Laying out children** (the common case) | `Stack` / `Inline` | `<Stack gap={4}>` |
| A component in `src/components/ui/` (shadcn/Radix) | Tailwind utility classes | `className="p-4 gap-2"` |
| An MUI-based component or an `sx` prop | `theme.spacing(index)` | `sx={{ p: 3, gap: 2 }}` |

All three land on the same pixel values. Do not convert between them by hand —
use the table below.

**Prefer `Stack`/`Inline` when you are spacing siblings.** They take the same
scale, but as a *type*: `gap={7}` (28px — not a step) is a compile error,
whereas `className="gap-7"` compiles happily and is quietly 4px off. See
**Components → Stack**.

## The scale

`spacing[i]` is **index-based**; the Tailwind class is **named for the pixel
value ÷ 4**. This is the single most common source of confusion: `spacing[3]`
is 16px, and 16px is `p-4`, not `p-3`.

### px or rem — they are not interchangeable here

The two tracks emit **different units**, and that has a real consequence:

| Track | What it emits | Under a user font-size change |
| --- | --- | --- |
| Tailwind (`p-4`) | `padding: 1rem` | **Scales** with the user's setting |
| MUI (`sx={{ p: 3 }}`) | `padding: 16px` | **Fixed** |

`spacing.ts` stores plain numbers and `src/theme.ts`'s `spacingFn` appends
`px`, so every MUI-spaced component is pinned to absolute pixels while every
shadcn component reflows. A user who raises their browser font size gets a
layout where half the components grow and half do not.

That matters for **WCAG 1.4.4 (Resize Text)**. It is not a defect in either
track on its own — it is a consequence of the two coexisting, and it is worth
knowing before choosing which to build a new dense layout in. Prefer the
Tailwind track for anything text-adjacent.

The `rem` column above is the conversion: divide px by 16.

## One scale, many utilities

The same 15 steps drive every spacing utility — padding, margin, gap, and the
sizing/inset families. Picking a step is one decision; which property you apply
it to is another.

| Family | Tailwind | MUI `sx` | Used here |
| --- | --- | --- | --- |
| Gap (flex/grid) | `gap-4` `gap-x-2` `gap-y-6` | `gap: 3` | **231** |
| Padding, all sides | `p-4` | `p: 3` | 90 |
| Padding, axis | `px-4` `py-2` | `px: 3` `py: 1` | 177 |
| Padding, one side | `pt-2` `pr-3` `pb-2` `pl-3` | `pt: 1` … | 42 |
| Margin, all sides | `m-4` | `m: 3` | — |
| Margin, axis | `mx-auto` `my-4` | `mx: 'auto'` `my: 3` | 7 |
| Margin, one side | `mt-4` `mb-2` | `mt: 3` `mb: 1` | 65 |
| Space between children | `space-y-2` `space-x-4` | — | 8 |

Counts are live usage in `src/components/ui/`.

### Prefer `gap` over margins

`gap-*` outnumbers every margin utility here roughly three to one, and that is
the house style rather than an accident. Gap spaces children from the parent, so
it cannot collapse, cannot double up against a sibling's margin, and leaves no
stray trailing space on the last child. Reach for a flex or grid container with
`gap-*` before adding `mb-*` to a list of items.

Margins are still right for pushing a single element away from its neighbours —
`mt-*` on a section heading, `mb-*` on a standalone block. Both are in the
system; the ordering is a default, not a prohibition.

Negative margins (`-mt-2`, `-mx-4`) exist and are used sparingly — 5 occurrences,
all for deliberate overlap such as pulling a border flush. They are legitimate
but should be commented where they appear.

### Physical vs logical properties

Tailwind offers both physical (`ml-` `mr-` `pl-` `pr-`) and logical
(`ms-` `me-` `ps-` `pe-`) directions. Logical properties flip automatically in
right-to-left locales; physical ones do not.

**Today this system uses 64 physical and 0 logical.** That is fine while every
consumer is left-to-right, and it is the single thing that would need changing
first if a right-to-left market is ever in scope. New components should prefer
`ms-`/`me-`/`ps-`/`pe-` where the choice is arbitrary, so the retrofit shrinks
rather than grows.

## Dense half-steps

Tailwind's default scale also offers **2px half-steps** (`1.5`, `2.5`, `3.5`)
that the MDS index scale does not contain. These are **permitted in dense,
list-like UI** — menu items, table rows, drawer rows, chips — where 4px is too
tight and 8px too loose.

| Class | px | rem | Where it is appropriate |
| --- | --- | --- | --- |
| `p-1.5` | 6px | `0.375rem` | Menu and dropdown items, compact chips |
| `p-2.5` | 10px | `0.625rem` | Table cells at compact density, drawer rows |
| `p-3.5` | 14px | `0.875rem` | Rare — prefer `p-3` (12px) or `p-4` (16px) first |

They are a deliberate sub-scale, not an escape hatch. Reach for a full step
first; use a half-step only when the full step is visibly wrong.

## What not to do

- **No arbitrary values.** `p-[13px]`, `gap-[7px]` and similar bypass the grid
  entirely. This is now **enforced** — see below.
- **Do not hand-convert between the tracks.** `spacing[6]` is 32px is `p-8`.
  Guessing produces `p-6` (24px) and a layout that is one step out.
- **Do not add a step to `spacing.ts` casually.** The scale is deliberately
  curated — 4px micro-steps at the small end, widening to 16px intervals at the
  large end. See the token request process before extending it.

## Enforcement

`npm run composition:check` reports, and `composition:check:strict` **fails**
CI (via `governance:ci`) on two things:

| Rejected | Why | Instead |
| --- | --- | --- |
| `p-[16px]`, `gap-[8px]` | An arbitrary value is a scale step spelled so it bypasses the scale | `p-4`, `gap-2` |
| `gap-7` (28px), `pr-9` (36px) | Compiles fine; not a value in `spacing.ts` | `gap-6`/`gap-8`, `pr-8`/`pr-10` |

`p-[var(--x)]` is allowed — reading a token is the sanctioned use of an
arbitrary value.

When the check was first run it found 20 arbitrary values and 5 off-scale
steps, including `gap-[8px]` five times. Those are fixed; the gate keeps them
fixed.

**Escape hatches:** `spacing-allow` on the line, `spacing-allow-file` in the
file. Legitimate for values derived from a control's **geometry** — the 28px
indent aligning checkbox helper text under its label, the 36px padding
clearing a calendar icon button — but not for dodging a spacing decision.
Say which in the comment.

A third check is **advisory and never fails**: physical properties
(`ml-`/`mr-`/`pl-`/`pr-`) over logical ones (`ms-`/`me-`/`ps-`/`pe-`).
Currently 61 physical, 0 logical. That number should shrink, not grow.

## Layout guidance

- Container padding: **16 / 24 / 32** (`p-4` / `p-6` / `p-8`) by breakpoint.
- Vertical rhythm in dense panels: multiples of **8** (`gap-2`, `gap-4`).
- Dashboard section gutters: **32–48** (`gap-8` … `gap-12`).
- Compact table rows: **6–10** via the half-steps above.
- Stacks and lists: a flex/grid parent with `gap-*`, not `mb-*` on each child —
  or better, `<Stack gap={n}>`, which cannot drift off-scale.
- Starting a whole page? Use the `PageShell` template rather than rebuilding
  the frame. See **Components → PageShell**.

### Control heights

Every interactive control — buttons *and* fields — shares one height scale,
defined in `src/components/ui/control-size.ts`:

| `size` | Height | Padding | Type | Icon |
| --- | --- | --- | --- | --- |
| `sm` | 32px (`h-8`) | `px-2.5` | `text-sm` | 14px |
| `md` | 40px (`h-10`) | `px-3` | `text-sm` | 16px |
| `lg` | 48px (`h-12`) | `px-4` | `text-base` | 20px |

The rule this enforces: **a control and a button declaring the same size are
the same height.** They constantly sit side by side — filter bars, search
rows, button groups — and nothing else checks it.

It did not hold before. `size="md"` meant 48px on a Button and 40px on an
Input and Select, so the button towered over the fields in every such row.
Four more controls (Textarea, Combobox, DatePicker, InputOTP) had no size
prop at all and had drifted to 40px, 32px and 40px respectively. The scale
now lives in one file and every control reads from it; a height defined
privately inside one component's cva block is how that drift started.

Two deliberate exclusions:

- **Textarea** takes the padding and type but no fixed height — its height
  comes from content and `rows`.
- **Checkbox, Radio, Switch** sit on their own scale. They are glyphs, not
  text boxes, and stretching them to 40px would look broken.

Grouped controls cascade: `<ButtonGroup size="sm">` and `<InputGroup size="sm">`
publish the size through context, so children inherit it and a group with a
mismatched child is not expressible by accident. A child's own `size` still
wins for the deliberate exception.

### Form rhythm

Forms are the densest nesting in the system, so the steps are fixed and
deliberately **tighten inward**:

| Level | Component | Class | px |
| --- | --- | --- | --- |
| Section — legend ↔ groups | `FieldSet` | `gap-6` | 24 |
| Between fields | `FieldGroup` | `gap-5` | 20 |
| Label ↔ control | `Field` | `gap-3` | 12 |
| Label ↔ description | `FieldContent` | `gap-1.5` | 6 |

Two constraints produced these, and both matter if you ever revisit them:

1. **Outer must be ≥ inner.** `FieldGroup` previously used `gap-7` (28px),
   which was *looser* than the `FieldSet` (24px) containing it — so fields
   read as less related to each other than to the heading above them.
2. **Inter-field spacing must stay clear of the field's own 12px internal
   gap.** At 20px the ratio is ~1.7×, enough to keep field boundaries
   legible. 16px (1.3×) was tested and rejected: it starts to blur which
   label belongs to which input.

Checkbox and radio groups collapse to `gap-3` (12px) at both levels, because
their rows are single-line and do not need field-sized separation.
- Genuinely two-dimensional layout belongs in grid utilities, not nested
  stacks — see **Foundations → Grid**.

## Corner radius

Radius sits on its own scale, and it is deliberately **not** overridden.

The Marsh DS standard radius is **2px** — small, squared-off, and a big part of
why the system reads as it does. That happens to be exactly Tailwind's stock
`rounded-xs`, so no configuration is required:

| Class | px | Use |
| --- | --- | --- |
| `rounded-none` | 0 | Flush edges, table cells |
| **`rounded-xs`** | **2** | **The DS default.** Buttons, inputs, cards, menus |
| `rounded-sm` | 4 | Larger surfaces — dialogs, sheets, popovers |
| `rounded-md` | 6 | Rare; prefer `sm` |
| `rounded-lg` | 8 | Rare |
| `rounded-full` | 9999 | Pills, avatars, badges |

### Why there is no override — and why that matters

`tailwind.config.js` used to rescale `borderRadius` around a `--radius`
variable, because shadcn's defaults assume `0.5rem` and this system wants 2px.
That override did real damage: it collapsed `rounded-md` to `calc(2px - 2px)` =
**0** and drove `rounded-sm` negative, so roughly **110 components silently
rendered square** while their class names said otherwise.

Under v4's scale the override is unnecessary — `rounded-xs` *is* 2px — so it
was removed and components were remapped (`md` → `xs`, `lg` → `sm`), keeping
their pixel values. The gain is that `rounded-*` now means the same thing here
as in any other Tailwind codebase, and there is one less override to drift.

**Do not reintroduce a `borderRadius` override.** If the DS radius ever
changes, change which class components use, or set `--radius-xs` in `@theme`
once — do not rescale the whole ladder around a variable again.

## Where the values live

- `src/spacing.ts` — the canonical array, exported as `spacing` and consumed by
  the MUI theme's `spacing` function (`src/theme.ts`).
- `dist/tokens.json` — the same 15 steps, exported under `spacing` for Figma and
  non-React consumers.
- Tailwind — **not configured**, because its default scale already matches. If
  the MDS scale ever gains a step that is not a multiple of 4px, Tailwind will
  need an explicit `extend.spacing` entry at that point.
