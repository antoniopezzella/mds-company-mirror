# Documentation Guidelines

This page defines how we write and structure design system documentation (MDX + Autodocs).

## Core Principles
1. Single source of truth: component APIs live in CSF stories (Autodocs); conceptual & foundational narratives live in MDX.
2. Keep MDX mostly narrative; move logic & rendering complexity into imported React helper components.
3. Prefer semantic clarity over visual cleverness—docs should be skimmable and linkable.

## Markdown / MDX Standard
We follow **GitHub Flavored Markdown (GFM)** where compatible with MDX.

Reference spec: https://github.github.com/gfm/

### Supported GFM Features We Use
- Tables (for tokens, comparison, matrices).
- Fenced code blocks with language hints (` ```tsx ` etc.).
- Autolinks & inline code spans.
- Task lists (only in contributor docs / not rendered inside Storybook nav yet) for internal checklists.

### Features to Avoid or Use Sparingly
- Raw HTML tags (e.g. `<button>`) inside prose—prefer backticks (`button`) to avoid parse edge cases.
- Deep nested lists (harder to scan). Flatten content or break into new sections.
- Excessive inline styling; use components or theme tokens.

## MDX Structure Rules
- Each MDX page must export a single `meta` object at the top with a `title`.
- Heading order: one `#` (title) then `##` level sections. Do not skip levels.
- Place future work / TODO notes in an italic block at bottom (`_Future: ..._`).
- Import helper components from `./_components/*` or root tokens (e.g. `../spacing`).
- Keep frontmatter out (not needed with Storybook’s indexer).

## Autodocs Integration
For components:
1. Add `tags: ['autodocs']` in the CSF default export (if you want the autogenerated docs tab).
2. Our authored MDX pages use a Controls‑only approach (no separate `ArgsTable` / `ArgTypes` blocks) because Controls already surfaces prop name, description, default & live editing.
3. Use the shared `<ApiSection />` component instead of manually placing `<Controls />` and variant `<Story />` blocks.
4. Only create a bespoke MDX page if narrative complexity (patterns, anti‑patterns, accessibility guidance) justifies it.

### ApiSection Usage Pattern
```mdx
// import { Story } from '@storybook/blocks';
// import * as ButtonStories from '../../components/Button/Button.stories';
// import { ApiSection } from '../Components/ApiSection';

// export const meta = { title: 'Components/Button' };

## Examples
<Story of={ButtonStories.Primary} />
<Story of={ButtonStories.Secondary} />

## Playground
<ApiSection primary={ButtonStories.Primary} variants={[ButtonStories.Secondary, ButtonStories.Danger]} />
```
Guidelines:
- Pass the primary (most representative) story to `primary`.
- List only meaningful variant stories in `variants` (avoid noise like trivial arg permutations).
- Omit `variants` if the component has a single canonical presentation.

## Referencing Stories in MDX
Prefer module/story references over string IDs:
`<Story of={ButtonStories.Primary} />` instead of `<Story id="components-button--primary" />`.
IDs are brittle during renames; story exports are refactor‑safe.

## Design Tokens
Tokens are code-first. MDX should render them dynamically so docs always match code (`ColorSwatches`, `TypographyTable`, `ElevationGrid`). Avoid copying values manually into tables.

## Accessibility Content
When documenting patterns, prefer: guidance list → example → counter-example (DO / DON’T) — plan a small `<DoDont />` block component for future expansion.

## Linting & Quality (Planned)
- Add a docs lint script to enforce: single `<Meta>`, no `<Story id=...>`, no deprecated `ArgsTable` / `ArgTypes` usage, heading depth.
- Visual regression (Chromatic) will track design token component diffs.

## Changelog Discipline
Any breaking token rename or removal must: (1) update token source file, (2) update affected MDX narrative, (3) annotate change in `CHANGELOG.md` under a Docs section.

## Quick Author Checklist
- [ ] File name ordered (e.g. `70-NewTopic.mdx`).
- [ ] Single `<Meta>`.
- [ ] Uses `<ApiSection>` (no manual `<Controls>` unless a special case).
- [ ] No raw HTML tags in prose.
- [ ] Logic refactored to helper component if > ~10 lines.
- [ ] Uses story `of={...}` references, not `id=`.
- [ ] Tokens pulled from source, not hard-coded.
- [ ] Future TODO (if applicable) placed at bottom.
