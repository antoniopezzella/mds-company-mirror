# Roles Layer

Roles are an intent-focused abstraction above semantic tokens. Components should prefer roles instead of referencing `semanticColors` or primitive tokens directly. This improves resilience when refactoring themes, adding new modes, or adjusting accessibility constraints.

## Why Roles?
- Decouples component styling from raw semantic token names
- Enables alternative mode mappings (e.g. high-contrast) without component churn
- Provides a vocabulary aligning design + engineering (text.primary, surface.subtle, status.success)
- Simplifies validation: we can test role → color resolution instead of every component path

## Usage Example
```tsx
import { getRoleColor } from 'src/theme/roles';

const Chip = ({ children }) => (
  <span style={{
    color: getRoleColor('text.secondary'),
    background: getRoleColor('surface.subtle'),
    border: `1px solid ${getRoleColor('border.default')}`,
    padding: '4px 8px',
    borderRadius: 8,
    fontSize: 12,
  }}>{children}</span>
);
```

## Choosing a border role

Three border roles look interchangeable and are not:

| Role | For | Contrast obligation |
|------|-----|---------------------|
| `border.default` | The edge of an interactive control — an input outline, a button border, anything a user acts on | **Gated at 3:1** (WCAG 1.4.11). Never swap it for a quieter token to soften a design. |
| `border.subtle` | Hairline rules *inside* a surface the user is already in — table row separators, list dividers, the grid shell | None. It is decoration, not a boundary. Tracked informationally so it cannot drift so faint it stops separating anything. |
| `border.strong` | Deliberate emphasis above the default weight | — |

`border.subtle` is **translucent in dark mode** (`rgba(255,255,255,0.10)`), not a
fixed grey. A hairline has to composite over whatever sits behind it — the page,
a raised panel, a pinned cell — and one fixed value cannot be correct on all
three. Drawing light mode's `#e3e3e3` on a near-black page produces the
brightest line on the screen, which is the bug this replaced.

## Choosing a surface role

`surface.raised` is a panel sitting *above* the page. In light it is the same
white as `surface.default` — paper on paper needs no lift, the border does that
work. In dark it is genuinely lighter (`#1a1a1a` against the `#101010` page), so
a grid or card reads as a surface rather than a hole cut into the background.

For a row's state, the roles are not interchangeable either: **selection** is
`surface.selected` (a brand tint — a state the user caused), while **hover** and
**striping** are `surface.subtle` (a neutral lift). Using `surface.accent` for
selection is a mistake this codebase has already made: it is one unit away from
`surface.subtle` in light, so selected and hovered rows rendered identically.

## Guidelines
- Introduce a new role only when multiple components share the intent and a semantic token name would leak implementation.
- Avoid duplicating semantic names as roles (e.g. no `textPrimary` role) — prefer `text.primary` pattern.
- Mark deprecated roles in future via metadata and surface during validation.
